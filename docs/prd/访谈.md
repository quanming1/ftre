# 访谈：F1 基于 cordis-py 的后端插件化重构

> 本文档按“用户提问 + 助手关键回答”记录需求访谈。它是 PRD 的参考材料，不替代 PRD；最终需求与验收标准以 `PRD-F1-backend-plugin-refactor.md` 的 approved 版本为准。

## 访谈 1：大型项目的插件化组织方式

### 用户提问

我计划以 `cordis-py` 作为 ftre 后端插件体系的基础。随着项目规模扩大，后端会包含大量 Plugin 和 Service，其中部分 Plugin 需要拆分成可独立开发、安装和发布的 Python 包。请分析这种架构下推荐的项目目录树，并重点说明：Plugin 与 Service 应如何划分边界、插件包之间如何解耦，以及宿主程序如何发现、配置、加载、卸载和更新这些插件与服务。

### 助手回答（关键内容）

核心原则：**Plugin 是部署与生命周期单元，Service 是 Plugin 对外暴露的能力契约。** 不应把每个类或每个 Service 都机械拆成独立包；只有需要独立开发、发布、启停或替换的功能才成为独立 Plugin 包。

推荐总体结构：

```text
large-project/
├─ pyproject.toml
├─ configs/
│  ├─ app.toml
│  └─ plugins.toml
│
├─ apps/
│  ├─ gateway/
│  │  └─ src/acme_gateway/
│  │     ├─ main.py
│  │     └─ bootstrap.py
│  └─ worker/
│     └─ src/acme_worker/
│        └─ main.py
│
├─ packages/
│  ├─ plugin-api/                  # 稳定契约，尽量小
│  │  ├─ pyproject.toml
│  │  └─ src/acme_plugin_api/
│  │     ├─ manifest.py
│  │     ├─ contracts.py
│  │     ├─ service_names.py
│  │     └─ errors.py
│  │
│  └─ plugin-runtime/              # cordis-py 上层封装
│     ├─ pyproject.toml
│     └─ src/acme_plugin_runtime/
│        ├─ loader.py
│        ├─ discovery.py
│        ├─ manager.py
│        ├─ config.py
│        └─ diagnostics.py
│
├─ plugins/
│  ├─ database-postgres/
│  │  ├─ pyproject.toml
│  │  ├─ src/acme_plugins/database_postgres/
│  │  │  ├─ __init__.py
│  │  │  ├─ plugin.py
│  │  │  ├─ service.py
│  │  │  ├─ config.py
│  │  │  └─ repository.py
│  │  └─ tests/
│  │
│  ├─ auth/
│  │  ├─ pyproject.toml
│  │  ├─ src/acme_plugins/auth/
│  │  │  ├─ plugin.py
│  │  │  ├─ service.py
│  │  │  ├─ domain/
│  │  │  └─ adapters/
│  │  └─ tests/
│  │
│  └─ orders/
│     ├─ pyproject.toml
│     ├─ src/acme_plugins/orders/
│     │  ├─ plugin.py
│     │  ├─ handlers.py
│     │  └─ models.py
│     └─ tests/
│
└─ tests/
   ├─ integration/
   ├─ contracts/
   └─ startup/
```

推荐依赖方向：

```text
apps ───────→ plugin-runtime ───────→ cordis-py
  │                  │
  └──────→ plugin-api ←──────── plugins
```

插件之间不直接依赖实现包。例如 `orders` 不应直接 import `database-postgres`，而应依赖 `plugin-api` 中定义的 `DatabaseService Protocol`，运行时通过稳定服务名（如 `ftre.database.v1`）取得实现。

独立包使用 Python 标准 package entry points 声明插件入口：

```toml
[project.entry-points."ftre.plugins"]
orders = "ftre_plugins.orders:plugin"
```

宿主使用 `importlib.metadata.entry_points()` 发现已安装插件，再根据 TOML 配置中的显式启用列表加载。发现与启用必须分离：安装一个包不代表自动运行它。

Loader 的核心流程：

1. 发现已安装插件入口，但不立即执行插件。
2. 读取启用列表与插件配置。
3. 校验插件名、API 版本、Manifest、配置和服务冲突。
4. 通过 `ctx.plugin(plugin, config)` 创建 Fiber。
5. 等待装载完成，检查 `ACTIVE`、`PENDING` 和 `FAILED` 状态。
6. 对长期 `PENDING` 的必需插件给出缺失依赖诊断。
7. 卸载、重启和更新分别映射到 `fiber.dispose()`、`fiber.restart()` 和 `fiber.update()`。

建议增加项目级 `PluginManifest`，至少描述：

- 插件唯一名称与版本。
- Plugin API 版本。
- 提供的 Service。
- 必需与可选依赖。
- 配置模型或配置 schema。

Service 公共接口建议使用 `typing.Protocol`，服务名应包含组织域和版本，例如 `ftre.database.v1`、`ftre.session.v1`，避免使用容易冲突的 `database`、`session`。

资源应通过 Cordis Effect 管理，并注意 LIFO 清理顺序：先建立底层资源 Effect，再提供上层 Service，使卸载时 Service 先下线、依赖插件先收到变化，最后释放底层资源。

需要多租户或多实例服务时，使用 `ctx.isolate()` 建立隔离域；配置作用域可结合 `ctx.intercept()` 与项目自己的配置层实现。

建议在 `cordis-py` 外封装项目级 `PluginManager`，提供 discover、load、unload、restart、update、status 和 unresolved_dependencies 等能力，而不是把插件发现、安装与配置治理继续塞进 Cordis 核心。

边界说明：`cordis-py` 提供的是进程内生命周期隔离，不是安全或故障隔离。不可信插件、依赖版本冲突插件或必须独立容错的功能，应运行在独立进程中，通过 RPC、消息队列或 Channel 暴露为远程 Service。

## 访谈 2：DeepSeek Harness 的项目管理与 Plugin / Service 分层

### 用户提问

请深入研读 `E:\deepseek-harness`。该项目是 DeepSeek 开源的 Agent Harness，底层使用 TypeScript 版本的 Cordis，并在其上扩展了大量 Agent 能力。请结合真实代码分析：它如何组织和管理大型 Monorepo，如何区分 Package、Plugin、Service、Provider 与 Consumer，如何发现并加载插件和服务，以及 Bundle、Profile、Agent Preset 分别承担什么职责。最后总结其中哪些设计适合用于 ftre 后端插件化重构，哪些复杂机制不宜在第一阶段直接照搬。

### 助手回答（关键内容）

#### 1. 总体判断

`deepseek-harness` 不是“一个 Agent 主程序加若干外挂插件”，而是一个由 Cordis 驱动的插件化 Agent 运行平台。Session、System Prompt、Tool Registry、LLM Adapter、Agent Registry、Agent Loop、持久化、Web UI 和启动器都通过插件参与组合。

其架构宣言是：没有一个需要不断修改的“特权核心”；新增行为优先通过挂载插件、注册 Service、监听事件或向现有 Registry 注册贡献完成。`packages/core` 虽然是稳定的产品 API 脊柱，但其中各组件在运行时仍然是可装卸、可替换的 Cordis Plugin。

关键概念必须分开：

| 概念 | 含义 |
| --- | --- |
| Package | 代码、依赖、测试、文档和发布的管理单元，一个 npm 包。 |
| Plugin | Cordis 的运行时装载、配置、启停和生命周期单元。 |
| Service | Plugin 之间通过稳定 `ctx.<key>` 暴露和获取的能力契约。 |
| Service Definition | 声明能力接口、类型、事件和稳定 Context Key。 |
| Service Provider | 提供该能力的具体实现，或向 Registry 型 Service 注册实现。 |
| Consumer | 使用 Service 的插件，常见形式是模型 Tool、UI、Hook、策略或 Agent Loop。 |
| Bundle | 一组 Cordis 配置行及相关代码的发行包，用来提供默认产品组合。 |
| Profile | 最终可启动的 Bundle 有序组合，加上用户安装的外部插件与配置覆盖。 |
| Preset | 单个 Agent 使用的局部插件组合，用于形成 Agent 私有的 Tool、Prompt、Skill 或 Service 视图。 |

#### 2. Monorepo 的项目组织方式

仓库使用 pnpm workspace，主要结构为：

```text
deepseek-harness/
├─ apps/                         # 最终产品入口
│  ├─ cli/                      # dsh 启动器
│  └─ web/                      # Web 应用
├─ vendor/                       # 内置维护的 Cordis 及配套插件
│  ├─ cordis/
│  ├─ loader/
│  ├─ include/
│  ├─ group/
│  └─ hmr/
├─ packages/
│  ├─ core/                     # 稳定的 Agent 产品 API 脊柱
│  ├─ llm/                      # LLM Capability Family
│  ├─ shell/                    # Shell Capability Family
│  ├─ subprocess/
│  ├─ fs/
│  ├─ sandbox/
│  ├─ session/
│  ├─ skill/
│  ├─ subagent/
│  ├─ workflow/
│  ├─ host/
│  ├─ client/
│  ├─ bundle/
│  └─ ...
├─ docs/
├─ examples/
├─ native/
├─ python/
└─ website/
```

当前代码快照中，`packages/` 下约有 226 个独立包、49 个功能组。仓库强制使用准确的两级结构：

```text
packages/<group>/<package>/
```

Group 只是功能分类和包地图的所有者，不能包含 `package.json`；真正的包只能位于第二级，不能扁平放置，也不能继续无限嵌套。

标准 Package 大致包含：

```text
packages/<group>/<package>/
├─ package.json
├─ README.md
├─ README.zh.md
├─ README.i18n.yaml
├─ tsconfig.json
├─ src/
│  ├─ index.ts
│  ├─ types.ts                  # 只放类型，不放运行时代码
│  └─ invariant.ts             # 本包自己的运行时不变量
└─ tests/
```

这使 Package 成为真正的所有权单元：公共契约、实现、测试、文档、运行时诊断和发布信息都由本包共同维护。

#### 3. Plugin 的两种主要导出形态

Service 类插件通过默认导出暴露：

```ts
export default class SomeService extends Service {
  static inject = ['dependency']

  constructor(ctx: Context, config: Config) {
    super(ctx, 'someService')
  }
}
```

函数插件使用命名导出：

```ts
export const name = 'some-plugin'
export const inject = ['someService']
export const Config = schema

export function apply(ctx: Context, config: Config) {
  // 注册 Tool、Adapter、Event Listener、Prompt Section 等贡献
}
```

项目明确禁止混用这两种形式：Service 包默认导出 Service Class；函数插件命名导出 `name`、`inject`、`Config`、`apply`，且不提供默认导出。这个约束来自真实 Loader 故障经验，而不是单纯的代码风格。

#### 4. Service Definition / Provider / Consumer 分层

项目把一项可替换能力称为 Capability Seam。完整 Seam 必须同时考虑：

```text
Service Definition ← Service Provider
        ↑
     Consumer
```

Provider 与 Consumer 都只能依赖 Service Definition，不直接依赖彼此的具体实现。只有当 Definition、Provider、Consumer 确实存在独立演进需要时才拆成不同 Package，不应为了追求包数量机械拆分。

##### Shell 能力链

```text
subprocess-local
      ↓ 提供
ctx.subprocess
      ↓ 使用
bash-local / bash-sandbox / pwsh-local
      ↓ 提供
ctx.shell
      ↓ 使用
tool-bash / tool-pwsh
      ↓ 注册
ctx.tools
      ↓ 使用
agent-loop
```

具体职责如下：

| 角色 | Package | 职责 |
| --- | --- | --- |
| Service Definition | `shell/shell` | 定义 `ShellExecutor`、执行请求、结果和进程句柄契约。 |
| Provider | `shell/bash-local` | 基于 `ctx.subprocess` 实现本地 Bash。 |
| Provider | `shell/bash-sandbox` | 在本地执行链上增加 Sandbox。 |
| Provider | `shell/pwsh-local` | 提供 Windows PowerShell 实现。 |
| Consumer | `shell/tool-bash` | 把通用 `ctx.shell` 包装为模型可见 Bash Tool。 |
| Consumer | `shell/tool-pwsh` | 把同一抽象包装为 PowerShell Tool。 |

`ShellExecutor` 不包含 Tool Schema、提示词、UI 或具体进程实现。`tool-bash` 只声明依赖 `tools`、`shell`、`systemPrompt`、`shellEnv`，因此替换 Shell Provider 不需要修改 Tool。

##### LLM 能力链

LLM 使用 Registry 型 Service：

```text
ctx.llm / LlmRuntime
├─ deepseek-official → DeepSeekAdapter
├─ 其他 provider     → PiAiAdapter
└─ replay            → ReplayAdapter
             ↓
         AgentLoop
```

`LlmRuntime` 是稳定 Service，同时维护 Provider Route 到 Adapter 的注册表。`llm-deepseek` 是函数插件，只依赖 `ctx.llm`，在 `apply()` 中调用：

```ts
ctx.llm.registerAdapter(['deepseek-official'], adapter)
```

这种模式适用于同一能力需要同时存在多个命名 Provider，并根据名称动态选择实现的场景。

##### Session 能力链

Session 被拆成内存事实源和持久化能力：

```text
SessionStore                  # 内存事件日志与运行时 Session
    ↓ session/event
SessionPersistence           # 持久化 Service Definition
    ├─ JSONL Provider
    └─ SQLite Provider
```

`core/session` 不直接实现数据库；持久化后端通过独立 Service Definition 与事件/flush 契约接入。因此 Session 领域模型与具体存储介质可以独立演进。

##### Agent 与 Agent Loop

Agent 公共契约和默认驱动也被拆开：

```text
Agent interface + AgentRegistry + Agent events
                       ↑
             AgentLoop default provider
```

UI、Tool、Hook、Subagent 等扩展依赖 `dsh-agent`，而不是直接依赖 `dsh-agent-loop`。这保证 Agent Loop 可以替换，而不会迫使所有消费者重写。

#### 5. Service 的注册与依赖激活

Service Definition 通过 TypeScript Declaration Merging 声明 Context Key：

```ts
declare module '@deepseek-ai/cordis' {
  interface Context {
    shell: ShellExecutor
  }
}
```

Provider 构造时调用：

```ts
super(ctx, 'shell')
```

Cordis 将实例注册到 Context 的 Service Store，并把注册行为绑定到当前 Plugin Fiber。Fiber 卸载时，Service 自动撤销。

Consumer 使用 `static inject`、命名导出的 `inject` 或配置 Row 的 `inject` 声明依赖。Loader 不依靠 YAML Row 顺序完成启动，而由 Service 可用性驱动：

1. Plugin 被发现并创建 Fiber。
2. Config Schema 被验证和补全默认值。
3. 必需 Service 不存在时，Fiber 保持 `PENDING`。
4. 依赖全部出现后，Plugin 进入加载并变为 `ACTIVE`。
5. Provider 消失时，依赖它的 Plugin 自动卸载。
6. Provider 再次出现时，Consumer 可以重新激活。

因此大量插件不需要集中写死手工启动顺序；依赖关系由各插件自己声明。

#### 6. Effect 与可逆注册

Tool、Prompt Section、Adapter、Provider Entry、Event Listener 等注册都必须是可逆 Effect：

```ts
ctx.effect(() => {
  const dispose = registry.register(contribution)
  return dispose
})
```

或者使用本身已经返回 Disposer 的 Registry API。Plugin 卸载或 HMR 时，相关贡献随 Fiber 一起撤销。

这意味着“插件卸载”不是只从插件列表删除一项，而是必须同时撤销：

- Service。
- Tool Schema。
- Event Listener。
- Prompt Section。
- Adapter Route。
- 后台任务、文件监听器、进程与其他资源。

#### 7. Bundle、Profile 与加载流程

Bundle 不是 Service，而是带有 Cordis Patch 的 npm 发行包：

```json
{
  "dsh": {
    "bundle": {
      "patch": "./cordis.patch.yml"
    }
  }
}
```

`dsh-base` 统一装入基础能力，如 LLM、Session、持久化、Tools、Shell、FS、Sandbox、Skill、Subagent、Workflow 和 Agent Loop。`dsh-web-app` 与 `dsh-headless` 在此基础上追加不同的应用表面。

Profile 是真正的部署组合，位于：

```text
$DSH_HOME/profiles/<name>/
├─ package.json                 # 外部插件依赖 + Bundle 顺序
├─ cordis.yml                  # 空根配置
├─ cordis.patch.yml            # 本 Profile 的用户覆盖
└─ node_modules/
```

配置层按以下顺序叠加：

```text
空配置
  → Bundle 1
  → Bundle 2
  → Profile cordis.patch.yml
  → Home cordis.patch.yml
  → --patch overlays
```

Patch 通过稳定 Row ID 替换完整 Config 或插入新 Row，后层优先。需要特别注意：针对已有 Row 的 Config 覆盖是整体替换而不是深度合并，用户必须重述希望保留的字段。

启动时：

```text
CLI
 ↓
读取 Profile 和 Bundle Manifest
 ↓
展开并叠加所有 Patch
 ↓
new Context()
 ↓
挂载 Cordis Loader
 ↓
提供启动期环境和命令行 Service
 ↓
Loader 导入所有 Plugin Row
 ↓
根据 inject 等待并激活插件
 ↓
审计 FAILED、PENDING 和未满足依赖
```

第三方插件通过：

```text
dsh plugin --profile <name> add <package>
```

安装到 Profile 自己的 `node_modules`。CLI 会检查安装包是否声明 `dsh.bundle`：Bundle 自动加入 Profile 的层列表；普通 Plugin Package 只完成安装，仍需要由配置 Patch 插入 Plugin Row。这里仍然保持了“安装”和“启用”两个不同概念。

#### 8. Agent Preset 的局部组合

Preset 解决“不同 Agent 使用不同插件集合”的问题，作用域查找链为：

```text
agent scope → preset scope → global scope
```

同一个 Preset 的插件树进程内只挂载一次，多个 Agent 通过 Scope Parent 加入该 Preset。Tool、Prompt、Skill 等贡献注册在 Preset Layer，各 Agent 按 `agent → preset → global` 的顺序解析，兄弟 Preset 之间互不可见。

Preset 有几个重要约束：

- Agent 必须在发布和开始首个 Turn 前加入 Preset。
- 已经产生会话历史的 Agent 不允许随意切换 Preset，避免旧 Tool Call 无法由新组合解释。
- Preset 决定模型可见 Tool 和 Prompt，因此选择结果必须写入 Session Log，保证会话可重建。
- Preset 中提供的 Service 必须放进 `isolate` Realm；否则 Service 会泄漏为进程全局，并在挂载审计中被拒绝。
- 已运行 Agent 保持原来的 Preset Generation，文件更新只影响后续新 Agent。

这是实现 Agent 私有能力集合的高级机制，不是简单地给每个 Agent 复制一份全局容器。

#### 9. 项目治理方式

该仓库不是 PRD 驱动流程。没有发现类似 ftre `docs/prd + TODO.yaml` 的正式 PRD 体系，主要使用以下机制管理大型项目：

1. **Agent Note 管理架构决策。** 非平凡修改必须在同一 PR 中新增或更新 Agent Note，按 `proposed / implemented / rejected / archived` 管理生命周期，并记录 Problem、Decision/Proposal、Alternatives 和 Consequences/Risks。
2. **Package 自治。** 每个 Package 自己维护 README、中文 README、API、测试、限制说明和运行时不变量。
3. **生成式架构文档。** Module Graph、Capability Seam Graph、Cordis API、Plugin Config Catalog、Tool Catalog、Persistence Catalog 都从代码生成并在 CI 中校验新鲜度。
4. **真实组合测试。** 产品可见 Plugin 不能只写手工 `ctx.plugin()` 单元测试，必须通过真实 `cordis.yml`、Loader 和应用进程验证用户可见、模型可见或持久化结果。
5. **卸载安全测试。** Registry Contribution 必须证明 Fiber Dispose 后贡献确实消失。
6. **强覆盖率。** `packages/*/*/src` 执行逐文件 100% Coverage Gate。
7. **统一包约束。** 所有 `@deepseek-ai/dsh-*` 包与根版本一致，内部依赖使用 `workspace:`，Cordis 同时作为 peerDependency 和 devDependency。
8. **Host / Client 分离编译。** 两侧使用独立 TypeScript Project Aggregate，避免双方对 Cordis Context 的同名 Declaration Merge 在同一 Program 内冲突。

#### 10. 优点、代价与风险

主要优点：

- Service 契约稳定，Provider 可替换。
- Tool、UI、Hook 和策略不绑定具体基础设施。
- 插件依赖声明取代集中式手工启动顺序。
- 所有注册都可逆，支持卸载和 HMR。
- Bundle 与实现分离，默认产品组合可覆盖。
- Profile 能安装外部插件并形成不同部署。
- Preset 能实现 Agent 级私有能力集合。
- 依赖图、配置文档和 Tool Schema 可以机械校验。

主要代价：

- 当前约 226 个 Package，导航和维护成本很高。
- 默认 `base` Bundle 的依赖与配置 Row 数量很大，成为集中式集成点。
- Patch 整体替换 Config，用户覆盖容易遗漏字段。
- Class Plugin 与 Function Plugin 的导出规则存在 Loader 约定成本。
- Scope、Realm、Isolate 和 Standing Preset Generation 的实现复杂。
- 所有 dsh Package 采用统一版本发布，会发布大量没有实质变化的包。

#### 11. 对 ftre 重构的建议

ftre 应借鉴原则，而不是复制包数量。

第一阶段建议吸收：

1. 明确区分 Package、Plugin、Service、Provider、Consumer。
2. 按 Capability Family 设计完整的 Definition / Provider / Consumer。
3. Consumer 只依赖 Service Definition，不依赖具体 Provider。
4. Plugin 通过显式依赖声明驱动激活，不在巨大 Bootstrap 中手工排序。
5. 所有 Service、Tool、Hook、Router 和后台资源注册都必须返回可执行的 Disposer。
6. 将默认组合放进 Base Bundle/配置层，不硬编码进 Plugin Runtime。
7. 安装、发现、启用、配置和装载必须是不同阶段。
8. 用真实启动组合测试 Plugin，而不仅是 isolated unit test。

第一阶段不建议直接照搬：

- 数百个独立发布包。
- Host / Client 双 Cordis Runtime。
- Agent Preset Standing Scope 和 Generation 管理。
- 大量动态自修改插件。
- 过早建立复杂的多 Realm Service 寻址。

更适合 ftre 的渐进落地顺序是：

```text
plugin-api
  ↓
plugin-runtime
  ↓
核心 Service Definition
  ↓
少量可替换 Provider
  ↓
Tool / HTTP / Hook Consumer Plugin
  ↓
Base Bundle 与配置覆盖
  ↓
稳定后再引入 Agent 私有 Preset / Scope
```

最值得写入 ftre 架构规范的一条原则是：**不要按文件数量拆包，而应按可替换能力与独立演进边界拆分；每个 Capability Seam 必须同时说明契约、Provider 和 Consumer。**

#### 2. 一级目录规则

一级目录只使用一种分类轴：能力族或基础设施层。

| 一级目录 | 唯一职责 |
| --- | --- |
| `boot` | 创建 Context、读取根配置、装配默认插件、启动和关闭应用。 |
| `plugin` | Plugin API、发现、加载、状态和诊断，不承载业务插件。 |
| `core` | Session、Tool、Agent 等稳定产品 API 脊柱。 |
| `session/channel/skill/mcp/context/schedule` | 各自完整的能力族。 |
| `host` | HTTP、WebSocket、API Gateway 等系统入口。 |
| `support` | 日志和诊断等没有业务语义的共享代码。 |

不再使用容易混淆的全局目录：

```text
contracts/
capabilities/
plugins/builtin/
infrastructure/
interfaces/
```

Service 契约、Provider 和 Consumer 回到其所属能力族中，不再按技术角色分散到全局目录。

#### 3. Builtin 不作为业务分类

`Builtin` 只是插件随主程序发布的来源属性，不是领域边界。原先集中在 `plugins/builtin` 的能力应回到所属 Group：

```text
plugins/builtin/skill           → skill/service 或 skill/filesystem
plugins/builtin/mcp             → mcp/global_client、mcp/private_client
plugins/builtin/title_gen       → session/title_llm
plugins/builtin/context_govern  → context/context_govern
```

内置插件和未来外部插件应遵守同一 Plugin API 和生命周期，只在发现来源与信任级别上不同。

#### 4. 二级 Unit 的职责规则

每个二级目录是一个可独立理解、测试并在未来提取为包的 Unit。统一内部模板为：

```text
<group>/<unit>/
├─ __init__.py                     # 只导出公共 API
├─ plugin.py                       # Cordis Plugin 入口
├─ config.py                       # 确实有配置时才创建
├─ service.py                      # 确实拥有 Service 时才创建
├─ types.py                        # 本 Unit 的公共类型
└─ ...                             # 私有实现
```

不要求每个目录机械创建全部文件；没有真实实现就不创建空壳、占位文件或 `TODO` 模块。

Unit 名称需要直接表达角色：

| 命名形式 | 含义 |
| --- | --- |
| `service` | 本能力族的稳定 Service Definition 或 Registry。 |
| `*_default` | 默认 Provider。 |
| `*_local` | 本地 Provider。 |
| `*_sqlite`、`*_filesystem` | 使用特定基础设施的 Provider。 |
| `tool_*` | 模型可见 Consumer。 |
| `*_bridge` | 两个 Service 或协议之间的桥接。 |
| `*_policy`、`*_govern` | Event/Hook 策略插件。 |
| `*_gateway`、`*_server` | 对外应用表面。 |

例如：

```text

```

应当能直接读出：

```text

        ↓

        ↓

```

#### 3. 为什么这版比「访谈 3」更适合 ftre

- `ftre/` 下不再平铺十多个同级能力，只保留四个导航层：`app`、`platform`、`services`、`features`。
- `app` 是进程入口和 Composition；`platform` 是 Cordis 接入；`services` 是稳定共享能力；`features` 是完整产品功能。依赖方向原则上是 `app → features → services → platform`，下层不得反向导入上层。
- 保留 `agent`、`session`、`channel`、`mcp` 等现有能力语义，只把它们放进清楚的上层分组，不增加含义模糊的 `core/`。
- 同一能力的 Service、Provider Plugin、Store、Tool 和 Router 仍然相邻；分组不会重新制造 `contracts/capabilities/interfaces` 式的跨目录跳转。
- `kernel/plugins` 只负责项目级发现、装载、状态和诊断，Cordis 已有的 Context、Service、Fiber、Effect 与事件机制不重复实现。
- 保持单个 `pyproject.toml`；未来某个能力需要独立发布时，再从清晰边界中提取包。

#### 5. Plugin 与 Service 的目标加载模型

第一阶段不为每个目录都创建 Service。只有被多个 Consumer 共享、拥有状态或需要生命周期管理的能力才是 Service，例如：

```text
config
message_bus
sessions
agent_profiles
agents
tools
commands
channels
http
mcp
skills
schedule
teams
attachments
```

`title`、`context_govern`、`plan` 等主要是行为插件：它们消费已有 Service，注册 Hook、Tool、Prompt 或 Router，不必为了目录对称再造一个空 Service。

几个容易混淆的具体角色如下：

| 能力 | Service | Provider Plugin | Server/内部实现 |
| --- | --- | --- | --- |
| Agent | `services/agent/service.py` | `services/agent/plugin.py` | `runtime/factory.py`、Loop、Mailbox、Compaction；均为私有实现 |
| HTTP | `services/http/service.py` | `app/gateway/http/service_plugin.py` | `server.py` 是 uvicorn 资源，`server_plugin.py` 负责最后启动和停止 |
| Session | `services/session/service.py` | `services/session/plugin.py` | Repository、JSON Store、Projection 是内部协作者 |
| MCP | `plugins/builtin/mcp/service.py` | `plugins/builtin/mcp/plugin.py` | Client/Adapter/Pool 是内部资源；MCP Server 是外部进程，不等于 ftre 的 HTTP Server |

这里的 Provider Plugin 可以提供一个或多个 Service；纯行为 Plugin 也可以一个 Service 都不提供。判断标准是：**Service 解决“别人怎么调用我”，Plugin 解决“我何时装载和卸载”，Server 解决“我监听什么网络协议”，Factory 只解决“内部对象怎么构造”。**

加载过程统一为：

```text
读取根配置
    ↓
创建 cordis.Context
    ↓
加载 Config、HttpService、MessageBus 等基础 Provider Plugin
    ↓
加载核心 Service 和默认行为 Plugin
    ↓
按配置加载外部插件
    ↓
等待 Router/Tool/Hook 等贡献就绪；强依赖缺失则启动失败
    ↓
最后加载 HTTP Server Plugin，开始接收流量
```

卸载时不再在 `main.py` 手写一长串反向清理，而是释放根 Context；Cordis 根据父子 Fiber 与 Effect 记录撤销监听、工具、命令、路由贡献和后台任务。

需要特别区分两类事件：

```text
EventBus / message_bus   = Channel → AgentLoop 的业务消息数据面
Cordis Context events    = Plugin/Service 的进程内扩展与生命周期控制面
```

二者名称、职责和测试必须分开。

#### 6. 第一阶段取舍

第一阶段立即完成：

1. 引入 `cordis-py`，移除重复 Plugin Kernel。
2. 建立唯一 Composition Root 和显式默认插件清单。
3. 按上表移动真实代码，拆解明显的多职责大文件。
4. 把配置、Tool、Command、Channel、Session 等共享能力变成有生命周期的 Service。
5. 消除 `main.py` 手工装配、API 模块全局 setter 和 Builtin 业务分类。
6. 保持当前外部协议、JSON 数据、AgentLoop 并发语义和 Octo 外部仓库边界。

第一阶段暂不完成，进入 TODO：

1. 仿 DSH 拆成大量独立 Python Distribution。
2. 完整 Preset、Isolate 与多 Agent 独立插件树。
3. Entry Point、远程 Marketplace、签名和权限沙箱。
4. 运行时增删 FastAPI Router；第一阶段 Router 只在启动 Composition 中生效。
5. 替换 JSON 持久化或迁移到 TOML。
6. 重写 AgentLoop、Mailbox、Compaction 等已经工作的核心算法。

#### 7. 第一阶段文件树验收标准

1. `src/ftre/plugin/kernel/` 不再包含与 `cordis-py` 重复的框架实现。
2. `main.py` 不再直接实例化所有业务对象，也不再手写完整关闭顺序。
3. 每个现有源码文件都能在目标树中找到唯一归属，没有为未来设想创建空模块。
4. `api/routes.py`、`ws_channel.py`、`agent_manager.py`、`skill_plugin.py`、`mcp_plugin.py`、`tools/cron.py` 的多职责被拆开。
5. EventBus 数据面与 Cordis 控制面拥有独立名称、接口和测试。
6. Plugin 的发现、启用和运行状态是三个不同概念；未启用插件不会因为被扫描到而自动运行。
7. Tool、Command、Hook、Router 与后台任务的注册都能随插件卸载撤销。
8. 现有 Session 数据、配置文件、WebSocket/HTTP 协议和 AgentLoop 并发不变量保持兼容。
9. 测试覆盖 Service 契约、插件生命周期、默认启动 Composition 和主要集成路径。
10. `app/platform/services/features` 各自有导航文档；每个能力说明 Owner、公共 Service、Provider Plugin、Consumer 和合法依赖方向。

最终目标不是让 ftre 的目录数量看起来像 DSH，而是让真实代码做到：**能力归属唯一、启动装配唯一、生命周期唯一、框架能力不重复实现，并且可以逐步演进。**
